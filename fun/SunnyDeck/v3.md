# SunnyDeck — Version 3 Roadmap

> Planning document written after full discussion (2026-08-01). Runtime source remains
> authoritative if it drifts from this document. Read `agent.md` (repo + SunnyDeck) before
> implementing any pillar.

---

## North star

**"As interactive as real life."**

Every character has a first-person history (who said what to whom, what they overheard),
a living relationship with *reasons* behind every emotion, a daily life the director
orchestrates, and a voice that is not a catchphrase loop. Rooms are physical spaces with
doors. The map is alive. Any OpenAI-compatible provider plugs in.

## Guiding principles (locked in planning)

1. **API cost is NOT a constraint** (~30M tokens/day). Prefer rich AI-driven systems over
   zero-cost stubs. Cadence/batching is used for sanity, not for cost.
2. **Whisper privacy is absolute.** A whisper is heard only by speaker + target — never
   overheard by radio, never in another character's log, never in their context.
3. **No retention caps on history** (user's explicit choice). Prompt *context windows* stay
   bounded per character even though storage is unbounded.
4. **Everything is additive.** Existing realms, sessions, settings survive. DB v2 is an
   additive upgrade (new `rooms` store only). Built-in providers (aqua, groq) unchanged.
5. **Architecture rules hold:** classic deferred scripts + shared globals, script order,
   custom dropdowns (no native selects), both UI skins, whisper privacy, lazy optional
   properties, `dbSanitize` `_`-key stripping, `SHARE_DENY_KEYS` key stripping.

## Pillar 1 — Per-character history + radio listening

### 1.1 Data model (hybrid: timeline + materialized logs)

- **Timeline stays the source of truth** (`sess.history[]`). Each entry gains:
  - `participants[]` — speaker + who was directly addressed (explicit target).
  - `heardBy[]` — characters in radio range at write time (computed from positions +
    radius + door state). Whisper entries: `heardBy = [speaker, target]` only.
- **Per-character logs are materialized lazily**: `sess.charLogs[key] = {syncedSeq, entries[]}`.
  Refreshed from the timeline by watermark (`syncedSeq`); appends only what's new.
  Whisper filtering happens here, in one place.
- Each log entry is tagged with its perspective: `role: 'spoke' | 'addressed' | 'overheard'`.
- **Legacy sessions**: logs build lazily on first access; no migration required.
- **No caps.** Soft bounded *prompt* window per character (last ~60–100 lines of their log).

### 1.2 AI context rule (the core change)

- `getReply()` context = **that character's own log only** (their words + addressed-to +
  overheard), plus spatial summary, memories (incl. overheard-tagged), relationship
  status, traits, voice pack, tone tags.
- **Never** the full omniscient timeline. Other people's dialogue is not injected into a
  character who didn't hear it.

### 1.3 Radio / adjustable radius

- `sess.radioRadius` replaces the fixed `EARSHOT_RANGE = 14` (default 14 → no behavior change).
- **Slider on the fullscreen map**, stored per session.
- One unified radius governs **both** responding (`inEarshot`) and overhearing (`heardBy`).
- Earshot ring visualization follows the radius.
- **SHOUT** bypasses radius: heard by every character in the session, lands in all their logs.
- **Whisper** never overheard; only speaker + target logs.

## Pillar 2 — Director & living world (AI-driven, cadence-based)

Replaces the timer-only ambient engine. **Zero-cost scheduling is rejected** — it chokes
realism; the director is an AI pass.

- **New settings** (global defaults, **per-session and per-room overrides**):
  - `directorModel` — a chat LLM for the director (selectable in Settings; essential).
  - `directorInterval` — messages between director passes (default 10).
- **On trigger** (after N messages, busy-flagged, never blocks chat): director returns a
  structured plan update:
  `{ schedule: [{key, activity, zone|room}], doors: [{room, state}], moments: [...], movements: [...] }`
- **Client primitives execute the plan**: `moveCharacter`, `setActivity`, door state,
  room enter/exit. Events recorded into logs + radio system.
- **NPC daily routines**: wake, eat, work at their chore, roam, enter/leave rooms, sleep —
  driven by the existing world clock.
- **Room-aware**: NPCs enter/leave rooms; director manages doors as ambient events.
- **Graceful failure**: malformed plans skipped with `console.warn`; busy flags prevent overlap.

## Pillar 3 — Rooms (physical, map-anchored, dual-mode)

### 3.1 Data model

- **New IndexedDB store `rooms`** (DB v2 additive upgrade):
  `{ id, name, description, characters[], messages[], rels{}, memories{},
     anchor?: {realmId, sessionId, zoneKey}, door: 'open'|'closed'|'locked',
     settings?: {directorModel, directorInterval}, createdAt }`
- **One continuous conversation per room** (no sub-sessions).
- **Dual mode (same feature):**
  - *Standalone* — a room with no map anchor (private scenario chat).
  - *Anchored* — the room is a physical building/space on a session map zone; door,
    radio, and spatial rules apply.
- **Character import from realms = snapshot copy**: fresh collision-safe key,
  `sourceRealmId` provenance, no live sync. Realm edits never mutate room characters.

### 3.2 Room mechanics

- **Chat**: direct-target, whisper, shout exactly like sessions. Everyone in the room is
  in range — no radius inside.
- **Three door states:**
  - `open` — anyone comes/goes freely; sound leaks both ways (shared soundscape).
  - `closed` — anyone comes/goes freely, but **no sound leak** (voice stays in the room;
    privacy, not imprisonment).
  - `locked` — no one enters or leaves; no sound leak; requires unlock (player action or
    director event).
- **Door flow is intent-driven, not a button row:** when the AI detects spatial intent
  ("let's go to the room"), the routing model physically moves the characters to the room
  on the map, then a small pop-up offers open/close/lock. Opening precedes entering a
  closed/locked room.
- **Audio scopes** (every conversation resolves to one): enclosed (occupants only) ·
  open (occupants + radius) · outdoors (radius rules). Whispers absolute in all three.
- **Searchable + export/import** like realms.

## Pillar 4 — Map (interactive, informative, alive)

Built on the current engine (zones, % positions, tokens, fullscreen + MOVE/D-pad/WASD,
zone editor) — grounded in `map.js`, `bigmap.js`, `mapedit.js`.

- **Adjustable radius slider** on the fullscreen map (per session).
- **Room anchors**: buildings/spaces on zones; door state visible on the map; enter/exit.
- **NPC chore movement**: director-driven walking between zones/rooms (walk animation exists).
- **Richer tokens**: activity label (not just emoji), mood, presence, relationship hint.
- **NPC chatter bubbles** on the map (`.mt-chatter` exists) — visible ambient life.
- **Earshot ring** per radius; weather/tint layers kept in sync (also in fullscreen).
- **Spatial summary** (prompt context) enriched with rooms, doors, activities, presence.
- `mapedit.js` zone editor stays; anchored rooms appear as editable placeables.

## Pillar 5 — Universal OpenAI-compatible providers

- **Settings shape**: `settings.customProviders[] = {id, name, base, apiKey, models[]}`.
  Field named **`apiKey`** so `SHARE_DENY_KEYS` stripping covers it (hard rule: keys never
  exported, never committed, never logged).
- **Runtime merge**: custom providers merged into `PROVIDERS` at load; built-ins
  aqua/groq unchanged; `parseModel` `provider:model` format unchanged (bare model → aqua).
  Custom `id` colliding with a built-in is rejected at add time.
- **Model fetching**: `GET {base}/models` with Bearer; success populates the provider's
  model list; **failure shows inline error and never blocks manual `provider:model` typing**.
- **Per-model gate**: `providerReady(modelStr)` replaces the aqua-only `hasApiKeys()`
  check at every call site — chat checks `chatModel`, ticks check `taskModel`, STT checks
  `sttModel`, etc.
- **TTS is Aqua-only**; custom providers are chat-capable; TTS button degrades gracefully
  (disabled + toast) when no TTS provider is configured. STT stays Groq whisper.
- Settings UI: Providers section — add/edit/delete provider, fetch models, assign
  chat/task/router/creative/tts/stt models from the combined list or type manually.

## Pillar 6 — System prompting (voice packs, layered prompt, romance)

The current prompt is a fact sheet + rules — it produces catchphrase loops (e.g. Nami
always fining berries) and flat emotional responses. v3 uses a **layered actor's briefing**:

1. **Identity** — description, personality, **traits**.
2. **Voice pack** — 2–4 exemplar lines per character (one casual, one emotional, one
   teasing). Hand-written for premade casts; **auto-distilled from the character's own
   history** for user-created/imported characters. The anti-generic fix.
3. **State** — current emotion + relationship status vs the player + memories
   (including overheard, tagged secondhand).
4. **Scene** — spatial summary, activity, world time/weather (exists).
5. **Steering** — never repeat phrases already used; react to THIS exact message; vary
   sentence structure; silence is allowed.
6. **Tone** — preset chips (`flirty / romantic / serious / playful / tense / angry /
   whisper`) + free-text tags (current `activeTags` promoted to real steering).

**Romance / intimacy** (relationship-aware, trait-aware, tasteful):
- Relationship engine's comfort/attraction axes feed the prompt; traits steer how each
  character handles advances (Sanji flirts, Nami deflects with wit until trust, Robin
  engages intellectually, Chopper flusters).
- Advances are in-character social moves that shift emotion axes; overstepping lowers
  them and the character says so in character, not as a system wall.
- Evolving relationship state is visible in UI so the dynamic reads as building, not random.

## Pillar 7 — Relationship engine (from scores to stories)

Replaces the single `affinity` number + tier labels. Approved sketch:

- **Per-pair directional vector**: `{hatred, love, jealousy, loyalty, friendship,
  happiness, comfort}`, −100…+100 (Zoro→Luffy ≠ Luffy→Zoro).
- **Seeded from existing affinity** on migration (map current scores into
  friendship/hatred baselines). Old `affinity`/`mood` stays until the engine ships.
- **Reasons ledger** (the core upgrade): every meaningful event appends
  `{ts, type, summary, deltas, observedBy[]}` — the model gets *why*, not just numbers.
- **Triadic dynamics**: a character's feelings shift when they **observe** interactions
  between others. Observation source = the radio/heard-log (Pillar 1) — only witnessed
  interactions count; bounded axes per observation to avoid combinatorial explosion.
- **Lifecycle**: persistent across sessions; decay so old grudges fade realistically;
  periodic AI-distilled per-pair "relationship summary" keeps context bounded.
- **Expression**: periodic system-prompt relationship-status notes (only what the
  character knows), so tone/topics/reactions shift with dominant emotions.
- **Scope**: per-container — realms keep realm relationships; rooms keep room
  relationships (imported characters start neutral in the new container).
- **Engineering guards**: strict validation of extracted deltas (known keys, clamped
  values, allowed emotion keys, reject garbage); AI-hallucinated reasons are dropped.

## Pillar 8 — UI: minimal skin redesign + unified action menu

- **Minimal skin redesign** (the next feature this session; retro untouched). The earlier
  minimal design was rejected as hideous; direction will be briefed at build time.
- **Unified action menu**: ONE button in the **composer row, right of the input** (same
  style as the direct-target selector — not a floating button) opens a small menu holding
  all secondary actions: whisper, dice, inventory, quests, sound, radio radius, doors,
  tags. **Principle: minimal buttons on the main screen.** The direct-target/mention
  selector stays visible.
- Implemented as an **action registry**: `{id, icon, label, enabled-when, handler}` used
  by both the toolbar and the menu — no orphaned actions.

## Cross-cutting — Character traits & memory

- **Traits**: simple per-character assignable tags ("brave", "a little flirty", "loyal
  to the captain"), edited from the character card, injected into prompts. Cheap; can be
  skipped if time-boxed.
- **Memory perspective upgrade**: with per-character logs (Pillar 1), memory distillation
  writes first-person memories including **overheard** content tagged secondhand
  ("I overheard…"), so the model knows it's not first-hand.

## Implementation order (phases)

1. **Providers** (foundation; low risk; unblocks everything)
2. **History/Radio + Director** (the heart: per-character logs, radius, heard-logs,
   director engine)
3. **Rooms + Map** (physical rooms, doors, map enrichments)
4. **System prompting** (voice packs, layered prompt, tone chips, romance)
5. **Relationships** (vector, reasons ledger, triadic, decay, seeding)
6. **UI + Action menu** (minimal redesign + unified menu)

Each phase: commit per feature, keep the app working between commits, `typeof`-guard all
cross-file calls.

## Compatibility & migration rules

- DB `sunny-deck-retro` → **v2, additive only**: create `rooms` store. No changes to
  existing stores/records.
- New settings keys: `customProviders`, `directorModel`, `directorInterval`,
  per-session `radioRadius`, room `door`; merge into `DEFAULT_SETTINGS`; old records
  inherit defaults (nested merge explicitly).
- Old sessions: charLogs built lazily; no data rewrite on load.
- Built-in providers and `provider:model` strings unchanged; `hasApiKeys()` becomes
  `providerReady(modelStr)` at call sites (keep the old name as a loose "any" check if
  the dashboard needs it).
- Export stripping: custom provider keys must never leave the browser (rely on
  `SHARE_DENY_KEYS` + `apiKey` naming).
- No native `<select>` controls; custom dropdowns everywhere.

## Phase 1 — Implementation brief (providers; written during Phase 1, 2026-08-01)

**Files changed:** `app.js`, `index.html`, `app-ai.js`, `dice.js`, `director.js`,
`inventory.js`, `journal.js`, `memory.js`, `quests.js`, `rewind.js`, `share.js`, `social.js`.

**Core mechanism:**
- Custom providers live in `settings.customProviders[] = {id, name, base, apiKey, models[]}`.
  `id` = lowercase slug (spaces stripped), must not collide with built-ins `aqua`/`groq`
  or other customs (rejected at add time).
- `mergeCustomProviders()` (app.js, near `PROVIDERS`): rebuilds the runtime `PROVIDERS`
  map — drops non-built-in entries, mirrors each custom provider's key into
  `settings['cp_'+id]`, sets `PROVIDERS[id]={base, keyName:'cp_'+id}`. This keeps every
  existing `const p=PROVIDERS[provider]; const key=settings[p.keyName];` fetch site
  working unchanged (6 sites: getReply, routeMessage, maybeAutoRename, generateRealmWithAI,
  aiJson, aiText).
- `providerReady(modelStr)` — per-model gate: parses provider, checks aquaKey / groqKey /
  custom apiKey. Replaces `hasApiKeys()` at all 13 gating call sites. `hasApiKeys()` is
  kept as a loose "any provider configured" check.
- `allModelOpts(baseOpts)` appends `id:model` entries from custom providers' fetched
  models into the creative/task/router/chat dropdowns. `refreshModelDropdowns()` re-inits
  dropdowns after provider changes.
- TTS stays Aqua-only (`speakChat` hardcodes `PROVIDERS.aqua` + `settings.aquaKey`, early
  return when aquaKey empty); STT stays Groq. Custom providers are chat-capable only.
- `cpFetchFor(cp)` — `GET {base}/models` with Bearer; returns model id array or `null`;
  never throws; inline error text; manual `provider:model` typing always available.

**Settings UI** (index.html, between API Keys and Models): `#cpList` (rows with
FETCH MODELS / REMOVE), name/base/key form, Fetch Models button (validates → fetches →
holds in `cpFetchedModels`), Add Provider (consumes fetched models), `#cpFetchResult`
status line. `bindCpControls()` called at top level; `renderCpList()` invoked from
`fillSettings()`; sSave calls `mergeCustomProviders()` before persisting; sReset clears
customs + refreshes dropdowns.

**Gate mapping** (which model each call site checks):
- `chatModel`: app-ai `handleChatSend`, rewind `regenerateReply`, share `novelizeSession`
- `creativeModel`: app.js `crGenerate` (controllerStr), quests `startQuest`
  (`realm?.creativeModel||settings.creativeModel`)
- `taskModel`: dice `rateDifficulty`, director `runAmbientBeat` + `stageDirectionTick`,
  inventory/journal/memory/questCheckTick/social ticks

**Verification performed:** `node --check` on all changed files (clean); Playwright
integration test with a mocked `GET /models` (all 10 checks passed: empty list hint,
fetch models, add provider, custom model appears in chat dropdown, per-model gate,
persistence across save+reload, built-in id collision rejection, remove, zero console
errors). Test pattern: `/tmp/providers-test.js` (serve `python3 -m http.server 8123`
from `fun/SunnyDeck/`, intercept `**/models`, drive the settings UI).

**Known limits:** no real end-to-end custom-provider chat was tested (needs a live key +
endpoint); TTS/STT remain built-in-only by design. Custom provider keys are stored in the
settings record (same plaintext pattern as aquaKey/groqKey) and are stripped from exports
via the `apiKey` field name + `SHARE_DENY_KEYS`.

## Phase 2 — Implementation brief (history/radio + director; written during Phase 2, 2026-08-01)

**Files changed:** `history-utils.js`, `app.js`, `app-ai.js`, `map.js`, `bigmap.js`,
`director.js`, `dice.js`, `inventory.js`, `quests.js`, `world.js`, `avatars.js`, `index.html`.

**Per-character history (hybrid):**
- `histPush(sess, h)` (history-utils.js) is now **the** write path for session history —
  it assigns a monotonic `seq` and calls `histTagEntry()` which computes
  `participants[]` (speaker + `whisperTo`/`targetKey`) and `heardBy[]` (everyone in
  radio range who isn't a participant). SHOUT → heardBy = all other characters;
  whispers → heardBy = [] (private, absolute).
- `histLastSeq(sess)`, `histDialogueSince(sess, watermark)` — seq utilities for
  cadence checks (legacy no-seq entries simply never count, which is correct).
- `syncCharLog(sess, charKey)` materializes `sess.charLogs[key] = {syncedSeq,
  entries[], syncedAll}` lazily: first access backfills the whole timeline (legacy
  sessions), later syncs append only seq > watermark. Whisper privacy is enforced
  in `charLogEntry()` — a whisper appears only in speaker + target logs.
- `buildCharLogLines(sess, charKey, limit)` — first-person prompt context:
  `You: …` / `X said to you: …` / `You overheard X say: …` / `You heard X shout: …`.
  `CHAR_LOG_PROMPT_WINDOW = 60`.
- **AI context rule:** `getReply()` now uses `buildCharLogLines(sess, responderKey,
  CHAR_LOG_PROMPT_WINDOW)` — each character sees ONLY their own log, never the
  omniscient timeline (fallback to `buildHistoryFor(...,-60)` if absent).
- **Reader UI:** clicking a portrait opens `openCharLogModal(key)` (app.js) — the
  character's first-person history with role tags (YOU / → you / 🎧 overheard /
  📢 heard) + a WALK OVER button. Player is the god-view reader; the model never is.
- All 12 history push sites now go through `histPush` (app-ai ×3, dice, director ×3,
  inventory, quests ×2, world ×2). NPC chatter lines carry `targetKey` so
  A→B exchanges read correctly in both logs.

**Radio / adjustable radius:**
- `radioRange(sess)` (history-utils.js) = `sess.radioRadius` or default 14. `map.js`
  `inEarshot`, `isNear`, `positionEarshotRing`, `spatialSummary` all use it.
- Slider in the fullscreen map top bar (`#bmRadius`, 4–40) writes
  `sess.radioRadius`, updates the earshot ring + far-token states, debounce-saves.
- The radius governs both responding and overhearing (one unified radius).

**Director engine (cadence-based AI):**
- New settings `directorModel` (default `aqua:deepseek-v4`) and `directorInterval`
  (default 10); per-session overrides read as `sess.directorModel`/`sess.directorInterval`.
- `directorPass(sess, realm)` (director.js) runs from `handleChatSend` after each
  exchange; fires when `histDialogueSince(sess, sess.lastDirectorSeq||0)` ≥ interval.
  Uses the director model via `aiJson`; returns `{movements, activities, moments}`
  executed through `moveToZone`/`setActivity`/`histPush` with strict validation
  (only realm characters, never the player, clamps). Busy flag + try/finally;
  failures are `console.warn` and never block chat.
- Gate corrections: ambient `runAmbientBeat` gates on **chatModel** (chatter/event
  beats call `aiJson(..., settings.chatModel)`); `stageDirectionTick` gates on
  **routerModel** (it calls `aiJson(..., settings.routerModel)`).

**Verification:** `node --check` on all changed files; Playwright integration test
(`/tmp/p2-test.js`, mocked `/chat/completions` + `/models`) — 9/9 passed: push tagging,
addressed/overheard roles, whisper privacy (never overheard), shout→all logs, char-log
modal, director pass (moves NPCs, logs moment, ignores invalid chars), radius slider +
ring, zero console errors.

**Known limits:** rooms/doors (Phase 3) will add `door` states to the audio model;
memory distillation still uses `buildHistoryFor` (perspective upgrade is a later
cross-cutting item); per-session director override is read-side only (no per-session UI
yet — comes with the action menu).

## Phase 3 — Implementation brief (rooms + map anchors; written during Phase 3, 2026-08-01)

**Files changed:** `rooms.js` (new), `app.js`, `app-ai.js`, `history-utils.js`, `map.js`,
`bigmap.js`, `search.js`, `quests.js`, `inventory.js`, `social.js`, `memory.js`,
`journal.js`, `director.js`, `rewind.js`, `index.html`.

**Persistence:** DB v2 additive — new `rooms` store; existing v1 realms/sessions/settings
survive untouched (upgrade verified). `dbPut('sessions', data)` routes `isRoom` objects to
the rooms store so the shared chat engine persists rooms with one code path.

**Room model:** `{id, isRoom, name, description, characters[], playerKey, messages[],
charLogs{}, moods{}, rels{}, memories{}, anchor:{realmId, sessionId, zoneKey}|null,
door:'open'|'closed'|'locked', settings{}, createdAt, lastActiveAt}`. One continuous
conversation per room.

**Engine reuse:** `roomAsSession(room)` installs a non-enumerable `history` getter
aliasing `messages` (JSON stays single-source) — so `addChatBubble`, `getReply`,
`buildCharLogLines`, whisper/shout/TTS, rewind EDIT/REDO all work unchanged.
`addChatBubble`/`showTyping`/`rerenderChat` target `#roomChat` when `currentSession.isRoom`.

**Write path:** `roomPush(room, h)` = `histPush` tagged against ROOM characters.
`queueRoomMirror(room, h)` — when `door==='open'` and anchored, dialogue (player + replies)
mirrors into the anchored session timeline as `kind:'ambient', mirrored:true` with
heardBy computed against the SESSION realm (in-range characters record it as overheard).
**Whispers never leak** (guard in the mirror; verified). Mirrors are serialized through a
promise chain to avoid lost updates.

**UI:**
- Dashboard `#roomsSection`: NEW ROOM / IMPORT ROOM / per-room OPEN · EXPORT · DEL.
- Room screen: header (back, name, door button when anchored, 🎭 play-as switcher),
  portraits (click → char log), chat, composer (mic, input, 🤫 whisper, target
  AUTO/SHOUT/char, send). Custom dropdowns only (no native selects).
- Create modal: name + description, characters via "+ New Character" or "Import from
  Realm" (snapshot copy, fresh collision-safe keys, `sourceRealmId` provenance, custom
  play-as dropdown).
- Export/import room JSON (`sunnydeck-room` format, `stripUnsafe`).
- Map: `.room-marker` on anchored zones (door-state color), click enters (locked →
  toast), `🚪 ROOM` button on the fullscreen map anchors a new room to the current
  session + player's zone.
- Search: Rooms + Room Messages groups.

**isRoom guards:** quests (start/tick/finish), inventory tick, social tick, memory
distill, journal, stageDirectionTick, rewind branch, `handleChatSend` — realm-bound
systems never run against rooms.

**Verification:** `node --check` all changed files; Playwright `/tmp/p3-test.js` — 13/13
(v1→v2 upgrade preserving a v1 realm, room create + realm import, dashboard list, engine
reuse with `history===messages`, send flow with mocked reply, in-room whisper privacy,

**Deferred (documented):** session→room leak direction (leak is one-way room→session);
director room-awareness (NPCs entering/leaving rooms); per-room relationship ticks and

## Phase 4 — Implementation brief (system prompting; written during Phase 4, 2026-08-01)

**Files changed:** `app-ai.js`, `app.js`, `index.html`, `rooms.js`, `social.js`,
`voicepacks.js` (new).

**Layered system prompt (`getReply`)** — six layers, replacing the old fact-sheet:
`IDENTITY` (description/personality/**traits**), `STATE` (relationship status +
memories + activity), `SCENE` (spatial + world + social), `CONTEXT` (quest/inventory/
roll/replied), `VOICE` (voice pack), `TONE` (active tags), then hardened RULES:
never repeat phrases, react to THIS exact message, let the moment breathe, and the
relationship/romance guidance (in-character comfort, never a system wall).

**Traits** — simple per-character tags (`c.traits[]`): edit field in both character
forms (create draft + realm detail), room-create rows, realm import carries them,
injected as "Traits that shape you: …". Optional per character; harmless when empty.

**Voice packs (`voicepacks.js`)** — prebuilt `PREBUILT_VOICELINES` for the 22 premade
characters (casual/emotional/teasing). `voiceLinesFor(c)` = `c.voiceLines ||
PREBUILT_VOICELINES[key]`. `ensureVoicePack(c, realm, sess)` lazily auto-distills a pack
from the character's own log (≥5 spoken lines, one task-model call, busy-flagged,
persisted to realm or room). `getReply` awaits it before building the prompt.

**Relationship state** — `relationshipStatusNote(charKey, realm, sess)` in social.js:
mood + bond-with-player (from existing affinity/mood; Pillar 7 will deepen it) → STATE layer.

**Tone chips** — `TONE_PRESETS = [flirty, romantic, serious, playful, tense, angry,
whisper]`; a chip row in the session composer and room composer. Chips toggle
`sess.activeTags` / `room.activeTags` (whisper chip toggles whisper mode instead);
getReply reads the same `activeTags` field for both, so the injection path is shared.
Free-text tags (`+ TAG`) still work alongside.

**Voice / TTS (user decision)** — default model is now **`aqua:mimo-v2.5-tts`**;
voicedesign/voiceclone are marked optional in the dropdown. TTS fields
(`#ttsFields`, `#ttsVoiceField`) are hidden until an Aqua API key is present
(`applyTtsVisibility()` on load, fillSettings, and live key typing).

**Verification:** `node --check` all changed files; Playwright `/tmp/p4-test.js` —
10/10 (7 chips render, chip toggle + lit state, prebuilt + auto-distilled voice packs,
captured real system prompt shows all layers incl. voice/steering/romance/own-log/tone,

## Phase 5 — Implementation brief (relationship engine; written 2026-08-01)

**Files changed:** `rels.js` (new), `app-ai.js`, `app.js`, `index.html`, `rooms.js`.

**Model** — per-pair DIRECTIONAL emotion vectors over
`EMOTION_KEYS = [hatred, love, jealousy, loyalty, friendship, happiness, comfort]`
(−100..+100), stored per-container: `realm.rels` / `room.rels`. Pair records:
`{key, dir:{charKey: vector}, ledger[], summary, seeded, updatedAt}`.
`relGetPair(container,a,b)` lazily creates a pair and **seeds once from legacy
`affinities`** (friendship = +score·0.6, comfort +0.3, happiness +0.2, hatred = −score·0.6).

**Mutation:**
- `relApplyEvent(container, from, to, deltas, type, summary, observedBy)` — clamps
  per-emotion deltas to ±20, clamps vectors to ±100, appends to the **reasons ledger**
  (cap 40, the "why it happened" story), touches `updatedAt`.
- `relObserve(container, observer, a, b, sentiment, summary)` — **triadic**: observer
  reacts to witnessing a↔b. positive → friendship+3/comfort+2/happiness+1 (jealousy if
  the observer loves b); negative → hatred+3/friendship−2/comfort−2; jealous → jealousy
  scaled by the observer's love for b. Only fires on existing pairs (bounded).
- `relDecay(container)` — emotions drift toward zero after ≥1 day; hatred/jealousy
  fastest, comfort/loyalty slowest (per-axis speeds).

**AI tick** — `relationshipTick(container, context)`: container = rels holder (realm or
room), context = history holder (session or room; same object for rooms). Fires after
≥6 new dialogue messages (`REL_MIN_NEW_MSGS`), task-model extraction of `events` +
`observations` with strict validation (valid keys, from≠to, clamps) and a
**hallucination-presence guard** (observations only for observers with fresh entries in
their char log). Wired from `handleChatSend` (`relationshipTick(realm, sess)`) and
`roomSend` (`relationshipTick(room, room)`); saves to the right store.

**Prompt context** — `relationshipNoteFor(charKey, realm, sess)` replaces the P4
placeholder in getReply's STATE layer (falls back to `relationshipStatusNote`): mood +
the character's own direction (top 3 emotions ≥15) + the pair summary — only what the
character knows, never the omniscient map.

**UI** — "Relationships" button on the realm detail screen opens `openRelPanel(realm)`:
pairs sorted by recency, both directions' active emotions, pair summary + last reason.

**Verification** — `/tmp/p5-test.js` 9/9: seeding, apply+clamp+ledger, triadic,
decay, mocked-AI tick (events applied, observation applied for a present observer,
fabricated observer skipped, **rels stored on realm not session**, saved to realms),
prompt-note + getReply injection, panel render, room tick persisted to the rooms
store, zero console errors.

**Deferred / notes:** observation requires the pair record to exist (no pair creation
from observation alone — bounded, intentional); relationship web visualization and
per-char emotion UI are part of the UI phase; the social `affinity`/`mood` legacy
system remains active alongside (new engine reads it once at seeding).
